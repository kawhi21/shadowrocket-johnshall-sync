# 版本快照与回退

## 自动发布的边界

合并后，原每日工作流仍在北京时间 10:23 运行。新增检查和发布步骤按以下顺序执行：

1. 测试及公共源码检查通过。
2. 上游下载、结构校验和顺序校验通过；未知格式直接失败。
3. 校验生成文件的哈希、数量和白名单字段。
4. 有变化时，一次提交全部三份生成文件；无变化不重复提交。
5. 对已提交的实际 HEAD 构建版本快照。先创建草稿 Release，上传后下载回读校验，再公开发布。

PR 检查只运行离线测试、扫描和快照构建，没有写入或发布权限。现有 iPad 不会因 PR 创建而改变配置。发布逻辑需在合并后通过第一次实际 Release 运行验收；目前的模拟测试不是生产发布证据。

## 快照内容

每个 Release 的标识为 `rules-` 加快照清单的完整 SHA-256。附带 `snapshot.json` 和可重复构建的 `snapshot.zip`。清单记录源提交及每个文件的哈希和长度，包内只允许公开规则、脱敏模板和署名文件；不会打包任意工作目录、私人备份或 Actions secrets。

包内两个基础配置的远程列表地址固定到该源提交，不追随 main。因此回退到包内的配置后，规则会停留在选定版本。它不会自动回到每日更新版本，恢复追随 main 需要用户主动选择。

相同内容重跑会验证现有 Release，不重复发布；草稿上传失败可重试。已公开资产若与本地预期不一致，停止并报告错误，不覆盖既有公开资产。管理员仍有 GitHub 平台权限；本项目没有替用户打开仓库级不可变 Release 设置，哈希不等于第三方数字签名，应从正确仓库的可信 Release 获取标识。

## 用户端回退：保护私人覆盖

1. 在 GitHub Releases 选择已验证版本，记录完整标签，从该版本下载 snapshot.zip 和 snapshot.json。不要从聊天、评论或不明镜像获取替代资产。
2. 在电脑使用仓库提供的脚本校验并提取到一个**不存在的新目录**：

   `python scripts/snapshot.py extract --zip path/to/snapshot.zip --tag rules-完整哈希 --out path/to/new-rollback-directory`

   脚本拒绝额外路径、重复文件、符号链接、异常大小和不匹配哈希；不会覆盖现有目录，也不执行包内文件。
3. 将包内 `templates/Johnshall-Auto-Rules.conf` 保存到测试设备，使用一个新的本地文件名，例如 `Johnshall-Rollback.conf`。
4. 先备份并复制当前个人扩展为测试副本，只将测试副本的“包含配置”指向回退基础文件。保留本地 AI-Stable 和原 AI 模块；不要用包内个人模板覆盖已有私人配置。
5. 主动选择测试副本、编译并执行分流检查。确认后再决定采用回退副本；操作可能切换当前配置，不能作为无人值守任务运行。
6. 恢复每日更新时，让扩展重新包含原本指向 main 两份规则的本地基础配置，编译后再次检查。原 iPad 当前正常时无需执行这些步骤。

## 维护者端回退

如需要恢复 main 上的规则，应在独立分支恢复**整套** proxy.list、reject.list 和 validation.json，运行全部检查并提交 PR，不只恢复其中一份。每日同步会在下次验证成功后继续采用上游新版本；若要保持冻结，应在管理员审查后暂时停用同步工作流，不能误称提交回退会永久冻结版本。

提交已成功但 Release 发布失败时，main 的合格规则仍然有效，旧 Release 保留。修复发布问题后重新运行工作流即可；不要重新上传或改写一个已经公开且校验不一致的版本。

参考：[GitHub CLI Release 创建说明](https://cli.github.com/manual/gh_release_create)。本项目使用草稿阶段完成校验，再发布；并未将多次 GitHub API 请求宣称为原子操作。
